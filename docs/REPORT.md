# TrialMatch: report

> **Status: draft.** The system and evals are done. The gold labels still need review and the reflection still needs writing. See "Before submitting" at the end.

## 1. Task and scope

TrialMatch compares a patient description with clinical-trial eligibility criteria. For each criterion it returns **met**, **not met**, or **insufficient data**, with a quote from the patient text as evidence. It then rolls these up into a verdict, and asks for the facts that would settle the most open criteria.

| Mode | User | Input | Output |
|---|---|---|---|
| Matcher | Clinician, patient | One patient | Ranked trials |
| Cohort | Coordinator | One trial, and patients chosen by hand or found by cohort search | Who could qualify |

Business logic in scope: hard age and sex filters, per-criterion checks, code-only verdicts, follow-up questions, refusals for off-topic and urgent input, and for advice requests. If the model is unavailable, the interface falls back to the rules and labels those results. Out of scope: trial location, real patient data. The tool is assistive, and final decisions belong to clinicians and study staff.

**Not vanilla RAG.** Retrieval only supplies candidates. The core is structured extraction, per-criterion classification with enforced evidence, and rule-based decisions.

**Related work.** The per-criterion design follows the idea of TrialGPT ([Nature Communications, 2024](https://www.nature.com/articles/s41467-024-53081-z)). No code was reused. Differences here: two modes on one engine, separate measurement of parsing against Chia, and abstention measured as a safety property.

## 4. Why these metrics

| Component | Metric | Why this one |
|---|---|---|
| Profile | Field-level P / R / F1, exact lab values | A missed fact and an invented fact cause different harm |
| Retrieval | Recall and precision over the judged pool, nDCG@10 against random, filter violations | Separates "can the query reach it" from "is it ranked well". Random gives nDCG a floor |
| Cohort search | Share of trials with an eligible patient in the top 10, eligible recall@10, nDCG@10, against conditions-only and random order | A coordinator screens a shortlist, so what matters is whether an eligible patient makes it. Two baselines show what each part adds |
| Parsing | Strict and relaxed entity F1 against Chia, per type | Strict alone punishes reasonable boundary differences. Relaxed alone hides them |
| Checker | Per-class P / R, macro-F1, not accuracy alone | Classes are imbalanced, and a system that always abstains can look safe |
| Evidence | Share of quotes verbatim, match with gold quote | A correct status with a wrong reason still misleads the reader |
| Abstention | Invented-decision rate on insufficient, flip rate | These are the errors that matter most, and macro-F1 buries them |
| Aggregation | Exhaustive truth table, missed blocks | It is deterministic, so test all of it, then measure the effect of upstream errors |
| Safety | Unsafe proceed rate, urgent recall | Stopping too rarely is the costly direction |
| Follow-up | Criteria settled correctly after an answer | The point of a question is to settle something |
| End to end | Eligible vs excluded P / R against "never block", nDCG against random | Baselines show whether the verdict adds anything |

95% intervals are shown where the sample is small: 64 pairs per split on the checker.

## 6. Reading the results

Numbers are in the first table above, from the test split with prompts frozen. Model: `gemini-3.5-flash-lite`, free tier. The baseline is the offline rule system. TREC rows use the same pool for both. Parsing changed once after the first test run (see "Trial structure" below). Test was run once more after that change, and its errors were not read.

### What the model improved

- **Checker.** Recall on `met` and `not_met` rose sharply, because the model connects a named drug to its class and reads loosely worded criteria. Flips stayed at zero on this set.
- **Follow-up.** Once an answer is added, the model settles the criterion correctly. The rules couldn't, since answers often use words outside their lexicon.
- **Profile and retrieval.** The rules found no query for many abbreviated TREC notes, and the model almost always finds one. Query precision and recall both rose.
- **Entities.** Clear gain on Condition, Drug, Procedure, and Value. This used 150 lines against 1,378 for the baseline, so per-type numbers are noisier.

### The main trade-off: F1 hides it

The two systems reach similar F1 on eligible against excluded (model 0.722, rules 0.701 on the same pool), but in opposite ways:

- The **rules** almost never block. They rarely wrongly block an eligible trial, but they catch few excluded ones, so they add little over "never block".
- The **model** catches far more excluded trials, but wrongly blocks many eligible ones.

For a screening aid this is a real choice. A wrong block hides a trial someone could join, and a missed block costs a coordinator some time. So the model's profile isn't simply better, and the wrong-block rate is the first thing to reduce. nDCG against random shows the model's ranking is better than chance on this pool, but the margin is modest, and a small pool makes this number noisy.

### Trial structure in parsing

All 39 dev errors on TREC were read by hand ([error_analysis_dev.md](error_analysis_dev.md)). 11 of the 25 wrong blocks came from parsing that lost the trial's structure: lists of alternatives read as requirements that all must hold, criteria for one subgroup ("For SPMS, ..."), sections about a donor or relative, several participant groups in one trial, and exclusions written inside the inclusion list. Parsing now marks these, and aggregation applies them in plain code. Criterion text and ids didn't change, so the model's prompts stayed the same for 432 of 443 trials and their cached answers were reused.

The cost is in the rules: on test, one more excluded trial is no longer caught (0.207 to 0.204), because a conditional criterion can't block alone. Segmentation scores didn't change. Six of the 11 cases remain: options written at the same level as their parent, alternatives one level up ("migraine with aura" or "without aura"), and trial text that is itself wrong.

### Cohort search, scored on TREC in reverse

The usual TREC use fixes a patient and ranks trials. Cohort search does the opposite, so the eval does too: for each trial, rank all 75 TREC patients and see where the patients judged eligible land. Unjudged pairs count as not relevant, as is usual for TREC. Trials with at least one eligible patient were split into dev and test by a hash of the NCT ID, 300 each. Settings were chosen on dev only, from the ablation in `evals/results/patient_search_offline_dev.json`. Adding the trial's inclusion criteria to the query gave the largest gain. Heavier weights differed by under 0.015, so the simplest was kept. Test was run once.

- **What it shows.** Keyword search is far better than random order at putting an eligible patient in a 10-patient shortlist, and the title, keywords, and inclusion criteria add to the condition alone.
- **What it doesn't show.** The eval uses TREC's short notes, but the app searches PMC case reports, which are longer and mention many conditions in passing (a family history, a negative test). On those, a mention isn't a diagnosis, so the shortlist shows the sentence that matched and screening decides. The 75 patients and their topics are shared by dev and test, so the split separates trials, not patients.
- **The age and sex filter** flagged a few eligible patients. On dev, three of four were TREC labels that contradict the trial's own age range, and one was a rules error (a boy read as female because his mother is mentioned). Flagged patients are ranked last, not removed. In the app, PMC's own age and sex fields are used instead of the rules.

### Where the scores are still weak, and why

- **Invented decisions.** This is the main open risk. The model sometimes decides a criterion the record is silent on, and quotes real but irrelevant text. It was much worse before the prompt fix on dev, and the rules are stricter here. The verbatim check can't catch this, because it proves a quote exists, not that it's relevant. A relevance check is the next improvement to try.
- **Wrong blocks on TREC.** From reading dev errors: about half follow the trial text where the TREC label is more lenient (a glioblastoma trial for an astrocytoma patient, "newly diagnosed" for a patient treated for years). Changing the system for these would teach it to ignore criteria. Most of the rest is trial structure that parsing still misses (above).
- **Strict Temporal and Person F1.** Low for the model even though relaxed scores are higher, so it mostly disagrees with Chia on span boundaries. Overlap is enough for this use.
- **Query recall.** About half the relevant judged trials are reachable, because a single-diagnosis query misses trials filed under related terms. Query expansion could help.

### High scores, and how much to trust them

- **Quotes verbatim, truth table, filter violations.** True by construction. They confirm the code does what it says, and say nothing about clinical quality.
- **Checker on vignettes.** Likely optimistic. The vignettes are short and clear and were written by a model. TREC is the harder and more credible test.
- **Safety.** The 24 cases were written alongside the rules, are not held out, and were used to fix a bug. Treat this as a regression test. New phrasing would likely score lower.
- **Segmentation.** Hand-written cases were written alongside the parser. The Chia round trip rebuilds text from already-split lines, so it doesn't test real messy formatting well.

### Model choice

Tried on dev: `nvidia/nemotron-3.5-super-vl:free` scored higher on the dev checker, including no invented decisions. It was dropped for quota (50 requests a day) and availability, not quality. So the chosen model isn't shown to be the most accurate, and a better model might cut invented decisions. Results are in `evals/results/archive/nemotron-dev/`.

### Next improvements, in order

1. A relevance check on quotes, to reduce invented decisions.
2. Catch the remaining trial structure: options at the same level as their parent, and alternatives one level up.
3. Try a stronger model on the same TREC topics.
4. Query expansion for retrieval.
5. A small labelled set of PMC case reports per trial, to measure cohort search on the text it actually runs on.

## 7. Limitations

- **Small gold set, single author.** 128 pairs, labelled by the same agent that wrote the rules. Independent review would likely change some labels.
- **Small model samples on TREC.** 2 trials per label per topic. Intervals in the table are wide, and one free model produced all the results.
- **Fallback isn't separately evaluated.** When the model fails, the interface uses the rules, whose quality is the baseline column above. A single result can mix model and rule trials, and each rule trial is labelled. Evals never fall back, so reported model scores contain no rule results.
- **Free tier.** Google may use submitted content and humans may read it, so only synthetic and public data may be sent. Model versions can change or be retired.
- **TREC mismatch.** Judgements date from 2021, while trial text comes from today's registry and may have changed. Merged records with new IDs aren't scored. The pool is sampled evenly across labels, so precision here isn't precision in the wild.
- **Prompt injection isn't measured.** Text is delimited, and the quote guard limits the damage, but no adversarial eval exists.
- **Rule checks can still be wrong.** Numeric rules parse real-world text with regexes. They abstain on complex wording, but the flip rate on test is not zero.
- **No location logic**, so a trial may be unreachable for the patient.
- **Unstable decisions on long trials.** A small, unrelated edit to the patient text can change many criterion statuses, because the model sometimes treats silence as a denial and sometimes doesn't. So a trial's confirmed share and verdict can shift between near-identical inputs. The evals don't measure this. A repeat-run test would.
- **Cohort screening has no condition check.** A patient whose record never mentions the trial's condition gets `insufficient_data` rather than a block, because silence isn't treated as evidence. Such a patient can rank above patients who have the condition and were blocked on another criterion. Example seen: a breast cancer patient on a type 2 diabetes trial. Cohort search reduces this by only shortlisting patients who mention the condition, but patients added by hand are not checked.
- **Cohort search is tuned on short TREC notes, not on case reports.** No labels exist for PMC, so how well it transfers to long case reports is unmeasured.
